# WeKnora 业务解决方案

本文从业务、用户和需求视角说明 WeKnora 能解决什么问题。能力判断来自 README、产品文档、前端页面、API 路由与后端服务扫描；不把尚未确认的二开设想描述为现有功能。

## 1. 一句话定位

WeKnora 将企业分散的文档和业务知识转化为一个有权限、可检索、可问答、可推理、可对外发布并可接入业务工具的知识基础设施。

它不只是“上传文档后聊天”，而是覆盖知识采集、加工、使用、分发、治理和评估的完整平台。

## 2. 主要解决的业务问题

| 业务问题 | 常见表现 | WeKnora 提供的解决方式 |
|---|---|---|
| 知识分散 | 文件散落在网盘、IM、Notion、语雀和个人电脑 | 多格式导入、外部数据源同步、统一知识库 |
| 找资料成本高 | 员工不知道去哪里找，也不知道用什么关键词 | 语义/关键词/图检索和自然语言问答 |
| 重复答疑 | 客服、售前、研发反复回答相同问题 | 基于指定知识库的问答、引用和可复用 Agent |
| 文件多但没有体系 | 文档只有目录，没有主题关系和持续整理 | Wiki 自动生成、页面关联和知识图谱 |
| AI 回答不可控 | 不知道答案从哪里来，可能访问越权资料 | 引用来源、租户/RBAC、资源归属和审计 |
| AI 无法完成复杂任务 | 普通聊天只能回答，不能组合检索和工具 | ReAct Agent、MCP、Web Search、sandbox skill |
| 知识服务难触达 | 员工或客户必须进入专门后台 | Web Embed、CLI、IM、小程序和 API |
| 效果无法量化 | 上线后只能凭感觉判断问答质量 | 数据集、检索/回答评估和处理链路观测 |
| 模型或云厂商绑定 | 成本、合规和已有基础设施难以兼顾 | 多模型、向量库、对象存储和私有化部署 |

## 3. 服务对象

### 企业员工

- 在统一入口查询制度、产品、项目和操作流程。
- 获得带来源的回答，减少人工翻阅长文档。
- 在飞书、企业微信、Slack 等原有工作环境中使用知识助手。

### 客服与客户成功团队

- 用标准知识库辅助回答产品使用、故障和政策问题。
- 将 Agent 嵌入官网、帮助中心或客户门户。
- 通过知识权限和回答规则控制不同客户看到的内容。

### 销售与售前团队

- 快速查找产品能力、客户案例、解决方案和竞品信息。
- 汇总多份材料，辅助形成方案、投标分析和会议准备。
- 将内部知识与受控 Web Search、业务工具结合。

### 产品、研发与项目团队

- 沉淀需求、设计、接口、故障复盘和项目交付经验。
- 将原始文档整理成结构化 Wiki 和关系图谱。
- 为新成员提供项目问答和上下文入口。

### 知识管理员与平台管理员

- 管理知识库、成员、角色、模型、数据源和存储。
- 观察文档处理、模型调用、任务队列和审计记录。
- 按部门、项目或客户隔离空间和资源。

### 开发者与集成团队

- 通过 REST API、Go client、CLI 或 MCP 接入现有系统。
- 扩展模型、向量库、存储、数据源、IM 或 Agent 工具。
- 在私有环境中部署并执行二次开发。

## 4. 九类业务解决方案

### 4.1 统一企业知识中心

将 PDF、Word、Excel、PPT、Markdown、网页、图片等内容，以及 Feishu、Notion、Yuque、RSS 等数据源汇聚为可治理的知识库。

适合建设：企业内部知识库、部门文档中心、产品资料库、客服知识库、制度流程中心和项目交付库。

### 4.2 企业知识智能问答

用户直接用自然语言提问，系统从其有权访问的知识库检索内容并生成带引用的回答。

适合回答产品规则、操作流程、制度政策、项目背景和长文档总结类问题。引用和检索过程可以帮助用户核验答案，而不是只接受模型结论。

### 4.3 复杂任务 Agent

Agent 可以在知识检索之外组合 Web Search、MCP 工具和 sandbox skill，完成多步查询、比较、整理和生成任务。

可二开为售前方案助手、客服处理助手、投标分析助手、研究助手、产品需求分析助手或合规辅助助手。

### 4.4 自动 Wiki 与知识体系建设

把一批原始文档整理成结构化、相互关联的 Markdown Wiki，并通过层级导航和知识图谱呈现关系。

适合项目知识沉淀、技术文档整理、行业研究资料、新员工培训和客户交付手册。

### 4.5 对外智能客服和产品助手

通过 Embed Channel 将配置好的 Agent 发布到官网、帮助中心、SaaS 产品或客户门户，并配置域名白名单、访问控制和频率限制。

同一平台可以为不同产品、客户或业务线提供使用不同知识库和规则的助手。

### 4.6 IM 内的知识助手

让用户在企业微信、飞书、Slack、Telegram、钉钉等渠道里查询知识和延续对话，减少切换系统的成本。

IM 平台回调使用各自签名认证；是否开放上传、群聊上下文和自动回复，应按企业信息安全政策配置。

### 4.7 多部门和多客户知识空间

通过 tenant、organization、member、Owner/Admin/Contributor/Viewer、资源归属和共享机制，划分公司、部门、项目或客户空间。

这让 WeKnora 可以从单团队工具扩展为多组织知识服务平台，但前提是二开功能继续遵循租户隔离和 RBAC 约束。

### 4.8 问答效果评估和运营

利用数据集、召回结果和回答指标比较模型、分块、检索配置与版本变化，配合 Langfuse 和处理 span 定位质量与性能问题。

业务上可形成“收集失败问题 → 补充知识/调整配置 → 回归评估 → 发布”的持续运营闭环。

### 4.9 私有化与基础设施适配

支持多种 LLM、Embedding、Rerank、向量数据库、对象存储和部署方式，使企业可以根据数据合规、成本、性能和既有基础设施进行组合。

标准版适合 Compose/Kubernetes，Lite 和 Desktop 更适合试用、个人或轻量本地场景；具体容量和支持等级需结合部署验证。

## 5. 典型端到端业务流程

### 内部知识助手

```text
管理员创建部门空间
→ 导入文件并配置数据源同步
→ 设置成员和知识库权限
→ 配置模型、检索和 Agent 指令
→ 员工在 Web/IM 提问
→ 查看回答与引用
→ 管理员根据失败问题持续补充知识和评估
```

### 官网智能客服

```text
整理对外可公开知识
→ 创建专用 Agent
→ 限制可访问知识库和工具
→ 创建 Embed Channel、域名白名单和限流
→ 嵌入官网/帮助中心
→ 观察问题、引用和失败情况
→ 更新知识与回答策略
```

### 专业岗位 Agent

```text
确定岗位任务和风险边界
→ 建设专业知识库
→ 通过 MCP/API 接入只读业务数据
→ 为高风险工具增加审批
→ 用真实任务集评估
→ 小范围试点
→ 根据审计和效果逐步扩大权限
```

## 6. 二次开发的价值落点

WeKnora 已提供通用知识平台底座。真正形成业务差异化的部分通常是：

1. 接入企业自己的文档源、数据库和业务系统。
2. 把隐性的岗位经验整理成知识和 Agent 指令。
3. 复刻企业现有角色、组织和审批边界。
4. 将助手嵌入员工或客户正在使用的渠道。
5. 用真实业务问题建立可量化评估集。

因此二开优先级不应是“再做一个聊天页面”，而应是数据接入、权限映射、业务流程、专业 Agent 和运营评估。

## 7. 推荐落地阶段

### 第一阶段：知识可用

- 汇聚一个高价值业务域的资料。
- 建立权限清晰的内部问答。
- 要求回答带引用，并建立首批真实问题集。
- 验证检索正确率、回答可用率和内容更新流程。

### 第二阶段：进入业务渠道

- 接入一个核心 IM、官网或业务产品入口。
- 建设客服、售前或产品使用助手。
- 建立反馈、失败问题和知识更新闭环。

### 第三阶段：从问答到执行

- 通过 MCP/API 连接 CRM、工单、订单或项目系统。
- 先开放只读查询，再逐步加入需要人工审批的写操作。
- 建立工具权限、审计、异常恢复和业务指标。

## 8. 能力边界与需求判断

- 知识问答质量取决于源内容、解析、分块、检索和模型，不是上传资料后自然达到可靠状态。
- 前端隐藏按钮不等于安全；权限必须在后端 Auth、RBAC、API-key capability 和资源访问层落实。
- Agent 能调用工具不代表应自动执行高风险操作；付款、删除、审批、外发等动作需要最小权限和人工确认。
- Wiki 是知识整理辅助，不能自动替代业务 owner 对事实、时效和责任的审核。
- 多模型、多存储表示具备适配能力，不表示所有组合具有同等成熟度和性能。
- 平台提供评估能力，但真实业务指标、验收阈值和 SLO 仍需项目方定义。

## 9. 新需求进入开发前应回答

1. 服务谁，解决什么高频或高成本问题？
2. 输入知识来自哪里，由谁维护，多久更新一次？
3. 哪些角色能看、能改、能分享、能执行工具？
4. 答案或动作出错的业务风险是什么？
5. 是否需要引用、审批、审计和人工兜底？
6. 成功指标是什么：查找耗时、客服解决率、答案采纳率还是任务完成率？
7. 这是本 fork 的差异化能力，还是适合贡献 upstream 的通用能力？
