### WeKnora 标准版上云步骤

本文面向首次把 WeKnora 标准版部署到一台 Linux 云服务器的场景。目标是部署 5 个核心服务，并让用户通过公网 IP 或 HTTPS 域名访问：

| 类型 | Compose 服务 | 默认对外端口 | 是否应暴露公网 |
| --- | --- | --- | --- |
| Web 前端与反向代理 | `frontend` | `80` | 是，仅暴露 80/443 |
| Go 主服务 | `app` | `8080` | 否，仅供本机诊断和前端内网调用 |
| Python 文档解析服务 | `docreader` | `50051` | 否 |
| 主数据库与默认向量检索 | `postgres`（ParadeDB/PostgreSQL） | `5432` | 否 |
| 队列与流状态 | `redis` | `6379` | 否 |

默认调用关系如下：

```text
公网用户
  -> frontend（Vue 静态页面 + NGINX）
  -> app（REST、SSE、RAG、Agent、异步 Worker）
     -> postgres（业务数据、BM25、pgvector）
     -> redis（Asynq、流状态、Pub/Sub、限流）
     -> docreader（gRPC 文档解析）
     -> 外部 LLM / Embedding / Rerank API
```

标准部署默认不需要单独部署 Qdrant、Milvus、Neo4j、MinIO、Langfuse 或 MCP Server。需要相关能力时再按 profile 增加，不建议首次部署直接使用 `--profile full`。

> 本文不包含 GPU 和本地大模型部署。资源评估按调用外部模型 API 计算；如果计划在同一台机器运行 Ollama，需要单独评估 CPU、内存或 GPU。

> **第一版本资源基线**：2 vCPU / 4GB 内存，暂不启用 Neo4j 及其他可选 profile。该方案以低并发、一次解析少量文档和外部模型 API 为前提；4 vCPU / 8GB 作为后续升配档。

## 一、云资源评估

### 1. 业务规模假设

当前已知规模：

- 使用人数约 10 人；
- 预计同时活跃用户约 2～4 人；
- 文档约 20 份；
- 文档原始体积合计约 100MB；
- 使用 PostgreSQL 作为默认关系数据库、BM25 与向量检索引擎；
- 使用本地 Docker Volume 保存上传文件；
- LLM、Embedding、Rerank 使用外部 API，不在本机运行模型；
- 暂不启用 Neo4j、MinIO、Langfuse、独立向量库及 `full` profile；
- 同一时间尽量只上传、解析一份大文档。

“100MB 大小”存在两种口径，本文默认按 **20 份文档合计约 100MB** 估算。如果是 **每份文档约 100MB**，总原始文件约 2GB，应采用下文的增强配置，并注意单文件上传限制。

### 2. 推荐购买规格

| 资源 | 第一版本规格 | 后续升级规格 | 说明 |
| --- | --- | --- | --- |
| CPU | 2 vCPU | 4 vCPU | 10 人规模的日常 API 并发较低；2 核解析速度会更慢，但不影响基本功能 |
| 内存 | 4GB + 2GB Swap | 8GB | 4GB 可以运行 5 个核心服务，但必须限制解析和 Worker 并发 |
| 系统/数据盘 | 50GB SSD 起，建议 80GB | 100GB SSD | 同时容纳镜像、PostgreSQL、上传文件、解析图片、日志和至少一份备份 |
| 公网带宽 | 5Mbps | 10Mbps | 5Mbps 上传 100MB 理论约 160 秒；经常上传大文件再升到 10Mbps |
| 公网 IP | 1 个 | 1 个固定公网 IP | 用于用户访问和域名解析 |
| GPU | 不需要 | 不需要 | 前提是使用外部模型 API |

针对当前规模，第一版本采用 **2 vCPU / 4GB 内存 / 2GB Swap / 50～80GB SSD / 5Mbps**。这是一套低预算、低并发配置，目标是先稳定提供知识库上传、检索和问答能力，而不是追求批量解析速度。

本地实测中，Docker 可用内存约 3.83GiB，5 个核心容器空闲时合计约 707MB，且没有 OOM 或自动重启，因此 4GB 并非无法运行。需要注意，本地 Docker 有 8 个可用 CPU，而第一版本云主机只有 2 vCPU；云端的主要差异会表现为文档解析更慢、并发任务更容易排队。

以下情况触发升配到 4 vCPU / 8GB：

- 单份文件接近 100MB；
- 经常同时上传、解析多份 PDF、PPT 或扫描件；
- 会启用 OpenDataLoader、OCR、知识图谱或大量 Wiki 生成任务；
- 计划在同机部署 MinIO、Neo4j、Langfuse 等可选组件；
- 解析期间内存持续超过 85%，或发生 OOM/容器重启；
- Swap 持续大量使用、Redis 队列长期积压。

### 3. 资源消耗拆分

以下数值用于理解容量来源，不是当前 Compose 已配置的硬性限制：

| 服务 | 典型资源特征 |
| --- | --- |
| `frontend` | 本地空闲实测约 15MB；按低配云环境预留 64～128MB |
| `app` | 本地空闲实测约 321MB；任务运行时按约 500MB～1GB 观察 |
| `docreader` | 本地空闲实测约 267MB；解析时可能升至 1～2GB 以上，是主要峰值来源 |
| `postgres` | 本地当前数据量下约 85MB；初期按约 256～512MB 观察 |
| `redis` | 本地空闲实测约 20MB；当前队列规模按 128～256MB 观察 |
| 操作系统与 Docker | 预留约 700MB～1GB；2GB Swap 只用于吸收短时峰值，不能替代内存 |

不要只按 100MB 原文件购买磁盘。文档解析可能产生页面图片、分块、向量索引和历史版本，Docker 镜像、数据库备份也需要空间。第一版本至少使用 50GB SSD，条件允许优先选择 80GB。

### 4. 100MB 文档与默认上传限制

项目默认单文件上限为 50MB：

```dotenv
MAX_FILE_SIZE_MB=50
DOCREADER_GRPC_MAX_FILE_SIZE_MB=50
```

- 如果 100MB 是 20 份文档的合计大小，并且每份均小于 50MB，不需要修改。
- 如果存在单份 100MB 文件，建议把两项都设置为 `120`，给协议开销留出余量：

```dotenv
MAX_FILE_SIZE_MB=120
DOCREADER_GRPC_MAX_FILE_SIZE_MB=120
```

如果服务器前面还有云负载均衡或宿主机 NGINX，也必须同步把请求体上限提高到至少 120MB，否则请求会在到达 WeKnora 前被拒绝。

### 5. 扩容观察指标

上线后重点观察：

- 主机内存持续超过 80%；
- 磁盘使用率超过 70%；
- 文档解析期间出现 OOM 或容器重启；
- Redis 队列持续积压；
- PostgreSQL 查询延迟明显升高；
- 外部模型 API 的限流和超时。

当前规模优先采用纵向升级（4GB 升到 8GB），暂时不需要把 5 个服务拆到多台机器。

## 二、部署前准备

### 1. 推荐部署形态

本文采用：

- 一台 Ubuntu Server 22.04 LTS 或 24.04 LTS 云主机；
- Docker Engine + Docker Compose v2；
- WeKnora 标准版 `docker-compose.yml`；
- PostgreSQL、Redis、上传文件都在本机持久化；
- 外部模型 API；
- 公网 IP 用于首次验证，域名 + HTTPS 用于正式使用。

### 2. 安全组规则

在云控制台配置安全组：

| 方向 | 协议/端口 | 来源 | 用途 |
| --- | --- | --- | --- |
| 入站 | TCP 22 | 仅管理员固定 IP | SSH 运维 |
| 入站 | TCP 80 | `0.0.0.0/0`、`::/0` | HTTP 与证书签发 |
| 入站 | TCP 443 | `0.0.0.0/0`、`::/0` | HTTPS 正式访问 |
| 出站 | TCP 443 | 允许 | 拉取镜像、调用模型和第三方 API |
| 出站 | DNS/NTP | 按云厂商默认 | 域名解析与时间同步 |

不要向公网开放：

- `8080`：app；
- `50051`：docreader；
- `5432`：PostgreSQL；
- `6379`：Redis。

Docker 发布的端口可能绕过部分主机防火墙规则，因此公网边界应优先依赖云安全组；`app` 端口同时绑定到 `127.0.0.1`。

### 3. SSH 仅允许管理员 IP 时的连接与排障

轻量应用服务器的 Ubuntu 镜像可能使用 `admin` 作为 Workbench 与 SSH 用户，不要直接假设用户名一定是 `root`。先通过控制台的 Workbench 一键连接确认实际用户名，再把本机公钥加入该用户的 `~/.ssh/authorized_keys`。

如果 SSH 报 `Operation timed out`，故障发生在公钥或密码认证之前，配置公钥本身不会解决超时。可按以下顺序检查：

```bash
sudo systemctl is-active ssh
sudo ss -lntp 'sport = :22'
sudo ufw status verbose
```

预期 SSH 为 `active`、监听 `*:22`，且没有宿主机防火墙阻断。VPN、代理或分流网络可能导致浏览器查询到的公网 IP 与 SSH 的真实出口 IP 不一致；可先用已向公网开放的 80 端口配合 `tcpdump` 确认直连出口，再检查 22 端口是否有数据包到达服务器。

如果服务器完全收不到 22 端口数据包，但本机能够访问其他服务器的 TCP 22，可在明确授权的短暂诊断窗口内临时把 22 放开，发起一次 SSH 连接，然后立即从服务器日志确认真实来源 IP：

```bash
sudo journalctl -u ssh --since '5 minutes ago' --no-pager \
  | grep '<实际SSH用户名>' \
  | tail -n 5
```

连接出现 `Permission denied (publickey)` 说明网络已经打通，只剩公钥认证问题。取得日志中的真实 SSH 来源 IP 后，必须立即把云防火墙的 TCP 22 恢复为该单个地址的 `/32`，不得长期保留 `0.0.0.0/0`。随后通过 Workbench 将本机 `.pub` 公钥追加到实际用户的 `~/.ssh/authorized_keys`，并设置目录权限为 `700`、文件权限为 `600`；确认公钥 SSH 登录成功后再继续部署。

### 4. 准备域名

正式环境建议准备一个域名，例如：

```text
kb.example.com
```

在 DNS 控制台添加 A 记录，指向云服务器的固定公网 IP。DNS 生效前可以先使用 `http://公网IP` 验证。

## 三、初始化云服务器

以下命令以 Ubuntu 为例。

### 1. 更新系统与安装基础工具

```bash
sudo apt update
sudo apt upgrade -y
sudo apt install -y ca-certificates curl git make openssl
```

### 2. 为 4GB 内存配置 Swap

第一版本建议配置 2GB Swap，用于吸收文档解析的短时内存峰值。先检查云镜像是否已有 Swap：

```bash
sudo swapon --show
```

如果没有输出，创建 2GB Swap 文件：

```bash
if [ ! -f /swapfile ]; then
  sudo fallocate -l 2G /swapfile
  sudo chmod 600 /swapfile
  sudo mkswap /swapfile
fi
sudo swapon /swapfile
grep -qF '/swapfile none swap sw 0 0' /etc/fstab \
  || echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

验证：

```bash
free -h
sudo swapon --show
```

Swap 只能避免短时 OOM，不能解决持续内存不足。如果解析期间长期使用超过 1GB Swap，应升级到 8GB 内存。

### 3. 安装 Docker Engine 与 Compose v2

生产环境建议使用 Docker 官方 apt 仓库，不使用便捷安装脚本：

```bash
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

sudo tee /etc/apt/sources.list.d/docker.sources >/dev/null <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF

sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker
```

验证：

```bash
sudo docker version
sudo docker compose version
sudo systemctl is-active docker
sudo docker network create weknora-install-check
sudo docker network rm weknora-install-check
```

官方安装说明：<https://docs.docker.com/engine/install/ubuntu/>

> `docker` 用户组等同于高权限。本文保留 `sudo docker`，不强制把普通用户加入该组。

### 4. Docker Hub 不可达时离线中转固定镜像（备选）

如果 Docker 已正常安装，但访问 `registry-1.docker.io:443` 超时，或者个人镜像加速器对目标标签返回 `MANIFEST_UNKNOWN`，不要改用 `latest`，也不要在 2 vCPU / 4GB 服务器上构建源码。可以在能够通过 VPN 访问 Docker Hub 的 Mac 上拉取固定的 `linux/amd64` 官方镜像，再通过 SSH 传到服务器。

> 阿里云个人镜像加速器并不是所有 Docker Hub 镜像的实时透明代理，可能没有较新的或社区命名空间下的固定标签。生产环境不要未经核验就换用第三方公共镜像代理；优先使用 ACR 企业版制品订阅，或使用下面可校验摘要的离线中转方案。

Mac 为 Apple Silicon 时，当前本地运行的镜像通常是 `linux/arm64`，不能直接导出给 `linux/amd64` 云服务器。即使本地已经有 `wechatopenai/*:latest`，也必须重新拉取目标版本和目标架构：

> WeKnora 0.7.2 在 Docker Hub 上的正式标签带 `v`，即 `v0.7.2`；`0.7.2` 会返回 `manifest unknown`。因此 `.env` 中的 `WEKNORA_VERSION` 也必须写成 `v0.7.2`。

```bash
docker pull --platform linux/amd64 wechatopenai/weknora-ui:v0.7.2
docker pull --platform linux/amd64 wechatopenai/weknora-app:v0.7.2
docker pull --platform linux/amd64 wechatopenai/weknora-docreader:v0.7.2
docker pull --platform linux/amd64 paradedb/paradedb:v0.22.2-pg17
docker pull --platform linux/amd64 redis:7.0-alpine
```

拉取完成后检查架构和远程摘要。所有镜像都必须显示 `linux/amd64`，并记录 `RepoDigests`，不要只依据可变标签判断内容：

```bash
docker image inspect \
  --format '{{.RepoTags}} {{.Os}}/{{.Architecture}} {{json .RepoDigests}}' \
  wechatopenai/weknora-ui:v0.7.2 \
  wechatopenai/weknora-app:v0.7.2 \
  wechatopenai/weknora-docreader:v0.7.2 \
  paradedb/paradedb:v0.22.2-pg17 \
  redis:7.0-alpine
```

为降低 Docker Desktop 导出大型合并归档时引擎中断或出现 `unexpected EOF` 的风险，逐个保存五个固定镜像。每个归档都只含 `linux/amd64` 平台，并立即进行 gzip 和 tar 两层完整性检查；必须启用 `pipefail`，否则上游 `docker image save` 失败可能被 gzip 的成功退出码掩盖：

```bash
set -o pipefail

docker image save --platform linux/amd64 wechatopenai/weknora-ui:v0.7.2 \
  | gzip -1 > weknora-ui-v0.7.2-linux-amd64.tar.gz
docker image save --platform linux/amd64 wechatopenai/weknora-app:v0.7.2 \
  | gzip -1 > weknora-app-v0.7.2-linux-amd64.tar.gz
docker image save --platform linux/amd64 wechatopenai/weknora-docreader:v0.7.2 \
  | gzip -1 > weknora-docreader-v0.7.2-linux-amd64.tar.gz
docker image save --platform linux/amd64 paradedb/paradedb:v0.22.2-pg17 \
  | gzip -1 > paradedb-v0.22.2-pg17-linux-amd64.tar.gz
docker image save --platform linux/amd64 redis:7.0-alpine \
  | gzip -1 > redis-7.0-alpine-linux-amd64.tar.gz

for archive in \
  weknora-ui-v0.7.2-linux-amd64.tar.gz \
  weknora-app-v0.7.2-linux-amd64.tar.gz \
  weknora-docreader-v0.7.2-linux-amd64.tar.gz \
  paradedb-v0.22.2-pg17-linux-amd64.tar.gz \
  redis-7.0-alpine-linux-amd64.tar.gz
do
  gzip -t "$archive"
  gzip -dc "$archive" | tar -tf - >/dev/null
done

shasum -a 256 \
  weknora-ui-v0.7.2-linux-amd64.tar.gz \
  weknora-app-v0.7.2-linux-amd64.tar.gz \
  weknora-docreader-v0.7.2-linux-amd64.tar.gz \
  paradedb-v0.22.2-pg17-linux-amd64.tar.gz \
  redis-7.0-alpine-linux-amd64.tar.gz \
  > weknora-images-0.7.2-linux-amd64.sha256
```

关闭 VPN、确认本机 SSH 出口仍在云防火墙 TCP 22 的 `/32` 允许范围后，将归档和校验文件传到服务器。不要在聊天中发送 SSH 私钥或口令：

```bash
scp -i ~/.ssh/id_rsa \
  weknora-ui-v0.7.2-linux-amd64.tar.gz \
  weknora-app-v0.7.2-linux-amd64.tar.gz \
  weknora-docreader-v0.7.2-linux-amd64.tar.gz \
  paradedb-v0.22.2-pg17-linux-amd64.tar.gz \
  redis-7.0-alpine-linux-amd64.tar.gz \
  weknora-images-0.7.2-linux-amd64.sha256 \
  admin@<云服务器公网IP>:/tmp/
```

在服务器上验证传输文件后导入镜像：

```bash
cd /tmp
sha256sum -c weknora-images-0.7.2-linux-amd64.sha256

set -o pipefail
gzip -dc weknora-ui-v0.7.2-linux-amd64.tar.gz | sudo docker load
gzip -dc weknora-app-v0.7.2-linux-amd64.tar.gz | sudo docker load
gzip -dc weknora-docreader-v0.7.2-linux-amd64.tar.gz | sudo docker load
gzip -dc paradedb-v0.22.2-pg17-linux-amd64.tar.gz | sudo docker load
gzip -dc redis-7.0-alpine-linux-amd64.tar.gz | sudo docker load
```

再次检查标签与架构。Mac 的 Docker Desktop 可能使用 containerd 镜像存储，而云服务器使用经典 Docker 镜像存储；离线 `docker load` 后本地 `Image ID` 或显示出的 `RepoDigests` 可能被重新计算，因此不能只要求这两个字段逐字相同。应以传输归档 SHA-256 全部通过、标签和架构正确、Mac 与服务器的 RootFS 层集合哈希逐项一致作为验收依据：

```bash
sudo docker image inspect \
  --format '{{.RepoTags}} {{.Os}}/{{.Architecture}} {{json .RepoDigests}}' \
  wechatopenai/weknora-ui:v0.7.2 \
  wechatopenai/weknora-app:v0.7.2 \
  wechatopenai/weknora-docreader:v0.7.2 \
  paradedb/paradedb:v0.22.2-pg17 \
  redis:7.0-alpine
```

Mac 和服务器分别对每个镜像执行以下检查（服务器命令在 `docker` 前加 `sudo`），比较输出的 SHA-256：

```bash
docker image inspect --format '{{json .RootFS.Layers}}' \
  wechatopenai/weknora-ui:v0.7.2 | shasum -a 256
```

五个镜像的 RootFS 哈希都必须逐项相同；任何一项不一致都不要启动 Compose。

离线导入路径下不要执行 `docker compose pull`。确认五个镜像齐全后，后续启动命令使用 `--pull never`，防止 Compose 再次访问不可达的远程仓库：

```bash
sudo docker compose -f docker-compose.yml -f docker-compose.cloud.yml \
  up -d --pull never
```

导入错误镜像时不要启动服务，重新拉取、校验并导入正确归档即可。只有在镜像摘要、容器健康状态和数据卷都验收通过后，才删除服务器 `/tmp` 中的大型传输归档以回收磁盘空间。整个流程不需要执行 `docker compose down -v`。

## 四、获取代码并确定版本

### 1. 区分代码仓库与镜像仓库

本次部署会使用两类仓库，不要将它们混淆：

- Git 代码仓库 `https://github.com/simbajigege/WeKnora.git` 用来获取 `docker-compose.yml`、`.env.example` 和其他部署配置；
- 应用运行时的 `frontend`、`app` 和 `docreader` 从 `wechatopenai/*` 官方 Docker 镜像拉取；
- PostgreSQL 使用 `paradedb/paradedb:v0.22.2-pg17`，Redis 使用 `redis:7.0-alpine`；
- 仅克隆 Git 代码仓库不代表容器会根据该仓库的源码自动重新构建。

第一版没有修改应用源码，因此采用“自己的 Git 仓库中的部署配置 + 腾讯发布的固定版本镜像”。不在 2 vCPU / 4GB 云服务器上构建源码镜像。

### 2. 克隆自己的代码仓库

建议安装到固定路径：

```bash
sudo mkdir -p /opt/WeKnora
sudo chown "$USER":"$USER" /opt/WeKnora
git clone https://github.com/simbajigege/WeKnora.git /opt/WeKnora
cd /opt/WeKnora
```

如果要与本地仓库精确一致，先在本地执行 `git rev-parse HEAD`，把结果作为目标提交，然后在云服务器执行：

```bash
TARGET_COMMIT=<从本地复制的完整commit>
git fetch --tags origin
git checkout --detach "$TARGET_COMMIT"
```

记录将要部署的提交：

```bash
git status --short
git rev-parse HEAD
cat VERSION
```

生产环境有两种版本策略。本次默认使用方式 A。

### 3. 方式 A：官方固定版本镜像（本次使用）

适合部署正式 Release。在 `.env` 中把 `WEKNORA_VERSION` 固定为明确版本，例如：

```dotenv
WEKNORA_VERSION=v0.7.2
```

不要在生产环境长期使用 `latest`，否则不同时间拉取的镜像可能不一致。该方式会从镜像仓库拉取以下应用镜像，而不是在云服务器上编译 Git 仓库中的源码：

```text
wechatopenai/weknora-ui:v0.7.2
wechatopenai/weknora-app:v0.7.2
wechatopenai/weknora-docreader:v0.7.2
```

### 4. 方式 B：精确部署当前源码提交（本次不使用）

如果要求云端运行内容与当前 Git 提交完全一致，应从源码构建三个核心应用镜像。前端构建还需要 Node.js 24 与 npm。

```bash
node --version
npm --version
```

第一版本的 2 vCPU / 4GB 云主机只负责运行，不建议在上面构建源码镜像。源码构建会额外占用大量 CPU、内存和磁盘，应在本地、CI 或独立构建机完成构建与镜像扫描，再把按 commit 标记的镜像推送到私有仓库。以下服务器构建步骤仅供临时排障或升配后使用。

项目构建脚本内部直接调用 `docker`。如果确实要在云服务器构建，需要让当前用户临时获得 Docker 权限，并重新登录 SSH 使组权限生效：

```bash
sudo usermod -aG docker "$USER"
```

Docker 用户组等同于 root 权限。构建完成后可执行 `sudo gpasswd -d "$USER" docker`，并再次登录；更推荐使用隔离的 CI/构建机。

Compose 在解析配置时要求 `.env` 存在，因此先创建模板；密钥和正式参数仍在下一节统一修改：

```bash
test -f .env || cp .env.example .env
chmod 600 .env
```

先拉取基础设施镜像：

```bash
sudo docker compose pull postgres redis
```

构建 app、docreader 和 frontend：

```bash
make build-images-app
make build-images-docreader
make build-images-frontend
```

构建脚本默认生成 `latest` 标签。为当前提交增加不可变标签：

```bash
COMMIT_TAG=$(git rev-parse --short HEAD)
sudo docker tag wechatopenai/weknora-app:latest "wechatopenai/weknora-app:${COMMIT_TAG}"
sudo docker tag wechatopenai/weknora-docreader:latest "wechatopenai/weknora-docreader:${COMMIT_TAG}"
sudo docker tag wechatopenai/weknora-ui:latest "wechatopenai/weknora-ui:${COMMIT_TAG}"
```

随后把 `.env` 中的版本设为该提交标签：

```dotenv
WEKNORA_VERSION=d823ef61
```

上面的 `d823ef61` 只是格式示例，实际值应使用 `echo "$COMMIT_TAG"` 的输出。

启动时使用 `--pull never`，避免本地构建镜像被远程同名镜像替换。

更正式的做法是在 CI 中构建、扫描镜像，并推送到私有镜像仓库；云服务器只拉取按 commit 固定的镜像。

## 五、配置生产环境变量

### 1. 创建配置文件

```bash

```

`.env` 已被 Git 忽略，但它仍包含生产密钥。建议把密钥主副本保存在云厂商 Secret Manager/密钥管理服务中，部署时再写入 `/opt/WeKnora/.env`，不要提交到代码仓库或聊天记录。

### 2. 生成密钥

`SYSTEM_AES_KEY` 必须是刚好 32 个 ASCII 字符：

```bash
DB_PASSWORD=$(openssl rand -base64 36 | tr -dc 'A-Za-z0-9' | head -c 24)
REDIS_PASSWORD=$(openssl rand -base64 36 | tr -dc 'A-Za-z0-9' | head -c 24)
JWT_SECRET=$(openssl rand -base64 64 | tr -dc 'A-Za-z0-9' | head -c 48)
SYSTEM_AES_KEY=$(openssl rand -base64 48 | tr -dc 'A-Za-z0-9' | head -c 32)
```

把生成结果安全写入 Secret Manager 和 `.env`。`SYSTEM_AES_KEY` 一旦用于加密模型、MCP 或数据源凭据，就不能随意更换；丢失后数据库中的加密凭据无法恢复。

## 六、为 Redis 增加持久化卷

当前标准 Compose 为 Redis 开启了 AOF，但没有给 `/data` 挂载命名卷。容器被删除并重建时，队列和流状态可能丢失。云部署还需要再次固定镜像，并为 2 核 4GB 主机设置容器资源上限。增加以下 Compose override：

```bash
cd /opt/WeKnora
tee docker-compose.cloud.yml >/dev/null <<'EOF'
services:
  frontend:
    image: wechatopenai/weknora-ui:v0.7.2
    cpus: "0.25"
    mem_limit: 128m
    pids_limit: 128

  app:
    image: wechatopenai/weknora-app:v0.7.2
    cpus: "1.00"
    mem_limit: 768m
    pids_limit: 512

  docreader:
    image: wechatopenai/weknora-docreader:v0.7.2
    cpus: "1.00"
    mem_limit: 1152m
    pids_limit: 512

  postgres:
    image: paradedb/paradedb:v0.22.2-pg17
    cpus: "0.75"
    mem_limit: 896m
    pids_limit: 256
    shm_size: 128m

  redis:
    image: redis:7.0-alpine
    cpus: "0.25"
    mem_limit: 192m
    pids_limit: 128
    volumes:
      - redis-data:/data

volumes:
  redis-data:
EOF
```

后续所有 Compose 命令都同时指定两个文件：

```bash
sudo docker compose -f docker-compose.yml -f docker-compose.cloud.yml config --quiet
```

> Redis 持久化不能替代备份。核心业务数据仍以 PostgreSQL、`data-files` 卷和 `SYSTEM_AES_KEY` 为主。

## 九、配置域名与 HTTPS

正式使用不要长期停留在公网 IP + HTTP。可以选择云负载均衡/应用网关托管证书，也可以在宿主机安装 NGINX。下面给出宿主机 NGINX 方案。

### 1. 把 WeKnora 前端改为仅本机监听

修改 `.env`：

```dotenv
FRONTEND_PORT=127.0.0.1:8081
FRONTEND_BASE_URL=https://kb.example.com
APP_EXTERNAL_URL=https://kb.example.com
```

重新创建 frontend 和 app：

```bash
sudo docker compose -f docker-compose.yml -f docker-compose.cloud.yml up -d frontend app
```

确认：

```bash
curl -I http://127.0.0.1:8081/
```

### 2. 安装宿主机 NGINX 与 Certbot

```bash
sudo apt update
sudo apt install -y nginx certbot python3-certbot-nginx
```

创建 `/etc/nginx/sites-available/weknora.conf`：

```nginx
server {
    listen 80;
    listen [::]:80;
    server_name kb.example.com;

    # 单份文件可能达到 100MB 时使用 120m；否则可保持 50m。
    client_max_body_size 120m;

    location / {
        proxy_pass http://127.0.0.1:8081;
        proxy_http_version 1.1;

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # WeKnora 聊天使用 SSE，外层代理也不能缓冲。
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
    }
}
```

启用并检查：

```bash
sudo ln -sfn /etc/nginx/sites-available/weknora.conf /etc/nginx/sites-enabled/weknora.conf
sudo nginx -t
sudo systemctl reload nginx
```

DNS 已指向当前服务器后申请证书：

```bash
sudo certbot --nginx -d kb.example.com
```

验证：

```bash
curl -I https://kb.example.com/
sudo certbot renew --dry-run
```

最终用户统一访问：

```text
https://kb.example.com/
```

## 十一、备份与恢复

至少备份三类内容：

1. PostgreSQL 数据；
2. `data-files` 上传文件卷；
3. `.env` 中的关键密钥，尤其 `SYSTEM_AES_KEY`。

### 1. PostgreSQL 逻辑备份

```bash
cd /opt/WeKnora
sudo install -d -m 0700 -o "$USER" -g "$USER" /opt/WeKnora-backups
BACKUP_DIR=/opt/WeKnora-backups
sudo docker compose -f docker-compose.yml -f docker-compose.cloud.yml exec -T postgres \
  sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' \
  | gzip > "${BACKUP_DIR}/postgres-$(date +%F-%H%M%S).sql.gz"
```

### 2. 上传文件备份

```bash
BACKUP_DIR=/opt/WeKnora-backups
sudo docker compose -f docker-compose.yml -f docker-compose.cloud.yml exec -T app \
  tar czf - -C /data files \
  > "${BACKUP_DIR}/data-files-$(date +%F-%H%M%S).tar.gz"
```

### 3. 密钥备份

把以下值保存到云 Secret Manager，不要只保留在服务器磁盘：

- `DB_PASSWORD`；
- `REDIS_PASSWORD`；
- `JWT_SECRET`；
- `SYSTEM_AES_KEY`；
- 模型与第三方服务 API Key。

建议每日数据库备份、每日或每周文件备份，并把备份复制到与云主机不同故障域的对象存储。至少每季度做一次恢复演练；未经恢复验证的备份不能视为有效备份。

### 4. 恢复演练

恢复会覆盖现有数据，必须先确认备份文件、进入维护窗口并阻止用户写入。先停止业务服务，保留 PostgreSQL 和 Redis：

```bash
cd /opt/WeKnora
sudo docker compose -f docker-compose.yml -f docker-compose.cloud.yml stop frontend app docreader
```

恢复 PostgreSQL 到空数据库：

```bash
DB_BACKUP=/opt/WeKnora-backups/postgres-YYYY-MM-DD-HHMMSS.sql.gz

sudo docker compose -f docker-compose.yml -f docker-compose.cloud.yml exec -T postgres \
  sh -c 'dropdb -U "$POSTGRES_USER" --if-exists "$POSTGRES_DB" && createdb -U "$POSTGRES_USER" "$POSTGRES_DB"'

gzip -dc "$DB_BACKUP" \
  | sudo docker compose -f docker-compose.yml -f docker-compose.cloud.yml exec -T postgres \
      sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" "$POSTGRES_DB"'
```

恢复上传文件卷：

```bash
FILE_BACKUP=/opt/WeKnora-backups/data-files-YYYY-MM-DD-HHMMSS.tar.gz

gzip -dc "$FILE_BACKUP" \
  | sudo docker compose -f docker-compose.yml -f docker-compose.cloud.yml run --rm -T --no-deps \
      --entrypoint tar app xvf - -C /data
```

确认 `.env` 中的 `SYSTEM_AES_KEY` 与备份时一致，再启动并验收：

```bash
sudo docker compose -f docker-compose.yml -f docker-compose.cloud.yml up -d
curl -f http://127.0.0.1:8080/health
```

## 十二、升级与回滚

### 1. 升级前

```bash
cd /opt/WeKnora
git rev-parse HEAD
sudo docker compose -f docker-compose.yml -f docker-compose.cloud.yml images
```

升级前必须：

- 完成 PostgreSQL、`data-files` 和密钥备份；
- 记录当前 Git commit 与镜像标签；
- 阅读目标版本变更记录；
- 先在测试环境验证启动、迁移、上传和问答。

### 2. 固定版本镜像升级

```bash

```

### 3. 回滚

如果新版本尚未执行不兼容数据库迁移：

1. 把 `.env` 中 `WEKNORA_VERSION` 改回旧版本；
2. 重新执行 `docker compose up -d`；
3. 验证健康检查、登录、检索、上传和问答。

如果数据库结构已经发生不兼容变化，仅回滚镜像可能不足。应在维护窗口中停止写入，恢复升级前的 PostgreSQL 和文件备份，再启动旧版本。

不要执行：


`-v` 会删除 PostgreSQL、上传文件和 Redis 的命名卷，造成数据丢失。
